係り受けのつながりや意味チェックを行うにあたって、カードに「タグ」を付与できるようにしました。

### タグの種類

| タグの種類 | 意味                               | 例                                                         |
| ---------- | ---------------------------------- | ---------------------------------------------------------- |
| ICanTag    | 能動的な能力として「何ができるか」 | can_walk（歩ける）, can_eat（食事できる）                  |
| ICanBeTag  | 受動的な能力として「何をされるか」 | be_eaten（食べられる）, be_chased（追いかけられる）        |
| IIsTag     | 分類として「何であるか」           | is_place（場所である）, is_animal（動物である）            |
| IIsAbleTag | 状態として「何になりえるか」       | is_ageable（歳を取りうる）, is_sizable（サイズ可変である） |

#### 例

- 名詞「猫」
  - Is
    - `is_animal`
  - IsAble
    - `is_sizable`, `is_weightable`, `is_speedable`, ...
  - Can
    - `can_walk`, `can_run`, `can_jump`, `can_eat`, `can_sleep`, ...
  - CanBe
    - `be_touched`, `be_watched`, ...
- 動詞「歩く」
  - Can
    - `can_walk`

つまり、「歩く」がつながる名詞は、`can_walk`を持つ名詞のみとなる。

- 「猫 + が + 歩く」→ OK
- 「本 + が + 歩く」→ NG

### 管理方法

以下はスプレッドシートで一元管理していました。

- カード（名詞、動詞、形容詞）

## 課題

### 「意味が通る文章」とは何か

自然な文章を判定しようとして、タグがどんどん細かくなっていきました。

例えば、`be_eaten`（可食）というタグは食材カードにつける想定でしたが、「ライオンが鹿を食べる」も成立します。そこで「アリが象を食べる」というような文章をOKとするかNGとするか悩みました（システム上はOKとしましたが）。

地味な知識かもしれませんが、「ダンゴムシがコンクリートを食べる」は成立しなくてはなりません。しかし「コンクリート」に `be_eaten`（可食）をただつけるだけでは、猫やパパがコンクリートを食べられることになります。意味にこだわればこだわるほど、草食や肉食、さらに細かい細分化が必要になっていきます。

「歩く」「飛ぶ」といった他の動詞も、それぞれ同じぐらい奥が深いです。

スプレッドシートを横に映しながら、少しテストプレイしてはタグの見直し、の繰り返しでした。

### 同音異義語の区別

幼児向けというわけで、画面上ではひらがなで表示していたのですが、「飛ぶ」「跳ぶ」のような同音異義語の扱いが困難でした。

結局「飛ぶ」だけを採用しましたが、もっと良い設計がなかったのだろうかと考えてしまいます。
